# Localisation — English, Japanese and Simplified Chinese — design

Date: 2026-08-24
Status: awaiting review

## Goal

The tray application is written in Japanese throughout. Add English and Simplified Chinese, pick
the language once when the application is installed, and fall back to English anywhere that choice
was never made.

## What the user asked for

- Add English and Simplified Chinese alongside the existing Japanese.
- Detect the language at install time. If it is one of the three, use it.
- Anything outside those three gets English.
- The zip download, which never runs the installer, defaults to English.
- The language can be changed afterwards from the settings window.

## Decisions

| Question | Decision | Why |
|---|---|---|
| When the language is decided | Once, at install time, and then it stays put | The user asked for install-time detection rather than following the OS. The application never reads the OS language at runtime. |
| Where the choice lives | `%AppData%\openinzone\settings.json`, key `language` | The same place the application already keeps per-user state. It outranks whatever the installer wrote. |
| How the zip gets English | By the installer's marker file being absent | No special case in the code. The zip simply lacks the file that would say otherwise, so the fallback applies. |
| Changing it later | A combo in the settings window's 全般 tab | Otherwise a zip user who wants Japanese has no way out of English but to hand-edit JSON. |
| Which Chinese | Simplified only, `zh-Hans` | The larger audience, and one translation to keep in step rather than two. |
| `zh-TW` / `zh-HK` | Out of range, so English | Follows from "Simplified only" plus "out of range gets English". Showing Simplified to a Traditional-script reader is worse than showing English. |
| Resource mechanism | RESX with satellite assemblies | The .NET standard. Keys become generated properties, so a typo is a compile error. Needs no change to the installer or the zip (see below). |
| Applying a change | Restart the tray, after asking | `x:Static` resolves once at startup. Restarting is honest; a window half in the old language is not. |
| CLI, Stream Deck plugin, README | Untouched, English | Scoped out by the user. The CLI and the plugin are already English-only. |

## Verified constraints

Checked on this machine before the design was settled:

- The tray publishes **self-contained but not single-file** (only the CLI passes
  `PublishSingleFile`). Satellite assemblies can therefore sit in `ja\` and `zh-Hans\`
  subdirectories the ordinary way.
- `installer/openinzone.iss` already copies the tray with `Flags: ... recursesubdirs`, and
  `release.yml` zips `dist\tray\*` wholesale. **Both pick up the satellite directories with no
  change**, so neither the installer nor the release workflow needs editing for packaging.
- Inno Setup 6 on this machine ships 29 `.isl` files, including Japanese and Korean, and
  **no Chinese at all**. Simplified Chinese is an unofficial translation and has to travel with
  the repository.
- `dotnet build src/OpenInzone.Tray -c Release` succeeds from WSL with 0 warnings, so the WPF
  project and its generated resource sources build on the Linux host the release is cut from.
- The strings needing translation in `OpenInzone.Control` amount to twelve: eight hotkey display
  names, three in `SnapshotText`, and one exception message. The Japanese in `UpdateInfo.cs` is
  inside a `///` comment and is not one of them.
- Outside the tests, `SnapshotText` and `HotkeyCommand.DisplayName` are read **only** by the tray.
  Nothing in the CLI, the daemon or the Stream Deck host touches either — checked across `src`,
  `tests` and `tools`. `SnapshotTextTests` does read `SnapshotText`, and that is what decides where
  the shared resources have to live; see "Resources".
- `tests/OpenInzone.Core.Tests` targets `net8.0` and references Core, Control, Ipc, StreamDeck and
  Cli — **not the tray**. The csproj says in a comment that this is deliberate so the suite runs on
  WSL, and the 361-test baseline for this branch was taken there.
- The CLI, the Stream Deck host (`KeyFace.cs` included) and the plugin manifest contain **no
  Japanese at all**. They are already English end to end and this change does not reach them.
- Searching for Japanese needs `\p{Han}`, not just the kana ranges. A kana-only search misses
  `FlyoutWindow.xaml.cs`'s `"未接続"` and both screenshot scripts, because 未接続 and 音量 are
  written in kanji alone.

## How the language is resolved

Three steps, in order, with no OS lookup anywhere:

1. `%AppData%\openinzone\settings.json` → `"language"`. What the user chose in the settings window.
2. `{app}\default-language`. A one-line file the installer writes with what it detected.
3. `"en"`.

Only `en`, `ja` and `zh-Hans` are accepted. An unrecognised value, an empty file, unparseable JSON,
or a `settings.json` with no `language` key at all, all fall through to the next step rather than
throwing — a corrupt preference should not stop the tray from starting.

Step 2 lives beside the executable rather than in `%AppData%` on purpose. An elevated install
writes to a different profile than the user who launched it, so a per-user path written from the
installer is not reliably the path the application will later read.

## Resources

Two resource sets, each owned by the assembly whose text it holds:

```
src/OpenInzone.Control/Resources/Strings.resx        SnapshotText's output, hotkey display names
                              Strings.ja.resx
                              Strings.zh-Hans.resx

src/OpenInzone.Tray/Resources/Strings.resx           window, tray and flyout text
                           Strings.ja.resx
                           Strings.zh-Hans.resx
```

with `<NeutralResourcesLanguage>en</NeutralResourcesLanguage>` on both projects. Satellite
assemblies for a referenced project are copied into the referencing project's culture
subdirectories, so both sets end up in the same `ja\` and `zh-Hans\` folders beside the tray.

**Why the shared strings stay in `OpenInzone.Control` rather than moving to the tray**, which an
earlier draft of this design proposed: `tests/OpenInzone.Core.Tests` targets `net8.0`, not
`net8.0-windows`, and does not reference the tray. Its own comment records that this is on
purpose — the tests are meant to run on the WSL side of a Windows machine, and they do. Moving
`SnapshotText` into a WPF, Windows-only assembly would put it out of reach of the tests that cover
it, and dragging the test project onto `net8.0-windows` to compensate would cost the whole suite
its portability to buy a tidier layer boundary. Not worth it.

So `SnapshotText` and `HotkeyCommand` stay where they are and stop holding literals. Resource
strings are not a UI dependency: `OpenInzone.Control` gains no reference to WPF and stays exactly
as portable as it is now.

The typed classes come from the SDK's `GenerateSource="true"`, not the Visual Studio designer,
because the release is built from WSL.

Keys are prefixed by the surface they belong to: `Settings_`, `Flyout_`, `Tray_` in the tray's set,
`Hotkey_` and `Status_` in Control's. XAML reads the tray's as
`{x:Static res:Strings.Settings_Title}`, and Control's across the assembly boundary as
`clr-namespace:OpenInzone.Control.Resources;assembly=OpenInzone.Control`.

`App.OnStartup` sets `CultureInfo.DefaultThreadCurrentUICulture` **before any window is
constructed**. A window built before that line would capture the wrong culture.

## What changes in OpenInzone.Control

Nothing moves out. The literals become lookups, in place:

- **`SnapshotText` stays put** and reads its ケース, ゲーム寄り and （ミュート） from
  `OpenInzone.Control`'s resources. Its own doc comment explains why it exists — two surfaces had
  each grown a copy of this formatting and disagreed — and that reason survives translation intact.
- **`HotkeyCommand.DisplayName` becomes a resource lookup** rather than a literal. `Id`
  (`volume-up`, `mic-mute`, …) is untouched: it is persisted as the key in `hotkeys.json` and
  referenced by IPC commands and the Stream Deck plugin, so **translating it would break every
  existing configuration**.
- `DeviceController`'s `InvalidOperationException` message becomes English. It is a log line for
  developers, and it crosses IPC as an error string; the tray catches the condition and shows its
  own localised text. `Ipc/IpcRoundTripTests.cs` asserts on this message and gets updated with it.

## Two different things called "language"

The settings window **already has a language combo**. `LanguageBox`, on the device tab, sets the
*headset's voice guidance* language — the voice that speaks in the earcups — and each item's `Tag`
is the byte the headset takes. It has nothing to do with what language the window itself is in.

After this change the window has two. They must not be confusable, by a reader or by the code:

| | Existing | New |
|---|---|---|
| `x:Name` | `LanguageBox` — **unchanged** | `UiLanguageBox` |
| Tab | デバイス | 全般 |
| Label | 音声ガイダンスの言語 | 表示言語 |
| What it sets | A byte sent to the headset | Which resources the tray loads |

`LanguageBox` keeps its name because two tools read the markup by `x:Name`
(`assets/make-settings-screenshot.ps1` and `tools/ShowSettings`) and would break if it moved.

Its three labels — 英語 / 日本語 / 中国語 — *are* window text, so they become resource lookups
like everything else. **The `Tag` bytes stay exactly as they are.** Getting that pairing wrong
once already shipped as far as a tag, with a headset speaking Chinese to someone who asked for
Japanese, which is why `VoiceGuidanceLanguageTests` exists.

## The UI language combo

In the existing 全般 tab, listing each language in its own script:

```
English
日本語
简体中文
```

Not "Japanese" and "Chinese" in English — a Japanese speaker staring at an English UI needs to
find their language without first knowing the English word for it.

Choosing one writes `settings.json` and asks: *restart to apply?* On yes, the tray relaunches. On
no, the choice is saved and takes effect next launch.

## Installer

Inno Setup has its **own** localisation mechanism — `[Languages]`, `.isl` files and
`[CustomMessages]` — and it is entirely separate from the RESX resources the application uses.
Nothing is shared between them: the same sentence appearing in both places is translated twice, in
two formats. The only thing crossing the boundary is the `default-language` file the installer
writes for the application to read.

- **English moves to the top of `[Languages]`.** Inno falls back to the first entry when the OS
  matches nothing, so as it stands a French machine gets a Japanese wizard. "Out of range gets
  English" is not true until this is fixed.
- `installer/lang/ChineseSimplified.isl` is vendored from the unofficial Inno Setup translations
  and registered as the third language, since the compiler does not ship one.
- The two `[Tasks]` descriptions, currently hard-coded Japanese, move into `[CustomMessages]` and
  are referenced as `{cm:...}` in all three languages.
- The existing `[Code]` section gains a post-install step that maps `ActiveLanguage()`
  (`english` / `japanese` / `chinesesimplified`) to `en` / `ja` / `zh-Hans` and writes
  `{app}\default-language`.
- `[Files]` is **not** touched. See "Verified constraints".

## Existing tests this breaks

Four test files pin Japanese text. **None of them may be deleted** — each was written because
something shipped wrong. They get rewritten to pin the same guarantee against resource keys
instead of against literal Japanese:

| File | What it pins now | What it must pin after |
|---|---|---|
| `Control/VoiceGuidanceLanguageTests.cs` | `Content="日本語"` ↔ byte | resource key ↔ byte |
| `Control/SnapshotTextTests.cs` | 14 assertions on 中央, ケース, 利用不可, （ミュート）… | the same output with the culture set to `ja` |
| `Ipc/IpcRoundTripTests.cs` (178, 180) | the `ヘッドセットに接続されていません。` error round-tripping | the English message, since that string becomes English |
| `Control/SettingsMarkupTests.cs` | no handler attributes under `DevicePanel` | unchanged — `x:Static` adds no handlers, but `DevicePanel`'s `x:Name` must survive |

## Tooling that reads the markup

Both `assets/make-settings-screenshot.ps1` and `tools/ShowSettings` locate elements by `x:Name`,
so **no `x:Name` in `SettingsWindow.xaml` may be renamed**. `assets/make-screenshot.ps1` and
`make-settings-screenshot.ps1` additionally hard-code Japanese sample text (`中央`, `音量を上げる`,
`現在のバージョン: 0.3.0`, …) to fill the mock window. They keep their Japanese: they exist to
regenerate the Japanese screenshots in `docs/images/`, and that is what those screenshots are.

## Tests

Added to `tests/`:

- Resolution order: `settings.json` beats the marker file beats `en`.
- Bad input — `fr-FR`, an empty string, malformed JSON, a missing directory — all give `en`.
- **Every key in each `Strings.resx` exists in its `.ja` and `.zh-Hans` siblings**, for both the
  Control set and the tray set. This is the one that earns its keep. A missing key does not throw;
  it silently serves the English string, so a half-translated build looks fine until someone reads
  it. The tray's resx files are read off disk as XML, the way `SettingsMarkupTests` already reads
  the markup, so the test needs no reference to the Windows-only project.

characters each is the actual size of the writing in this change.

## Translation provenance

Japanese is the existing text moved into resources, so nothing is newly translated there. English
and Simplified Chinese are written as part of this work and have **not had a native review**. That
is a known weakness of this change, recorded here so it is not mistaken for verified copy;
corrections are welcome by issue.

## Out of scope

The CLI's output, the Stream Deck plugin manifest, a Chinese README, and Traditional Chinese. The
first two need no work in any case: both are already English throughout.

`docs/images/*.png` stay Japanese. They illustrate `README.ja.md` and are regenerated by the
screenshot scripts above. English and Chinese screenshots would mean three sets of images to keep
in step with every UI change, which is a bigger commitment than this change should make on its
own. Recorded as a known gap.

## Delivery

`main` is protected as of 2026-08-24 and rejects direct pushes even from the owner. This goes in
as a branch → PR → squash merge, from the worktree `.claude/worktrees/i18n` on branch
`worktree-i18n`, based on `dbdba71`.

The PR needs one of the labels `enhancement` / `bug` / `fix` / `protocol` / `documentation`,
because the release notes are generated from merged PRs. **The PR title becomes the line users
read in the release notes**, so it is written for them, not for the diff.
